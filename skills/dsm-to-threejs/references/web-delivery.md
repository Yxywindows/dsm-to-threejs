# three.js Web 交付

仅当用户明确要 three.js/Web，或这次三维到 Web 的意图已清楚时执行。用户只要模型就按模型任务交付，不附加 Web 工程。若用户已有模型且只要 Web，先检查并读取现有模型，跳过建模和场景资产 brief；会改变场景几何、布局、颜色、材质时，必须先按主 skill 建并分享任务 brief。

## 1. 检查项目与输入

- 从当前项目根读取 `AGENTS.md`、包管理文件、three.js 与构建器的已装版本、入口页面、GLB 和任务记录。沿用已有框架/版本，不替用户升级或另起框架。
- 对已有 GLB 存在历史记录时，先核对记录中的内容 hash；无历史验收记录时不要求用户提供旧 pass，也不阻塞：本次先只读检查输入可读性、GLB scene/node、材质绑定与纹理像素，记录文件 hash 和本次检查基线，再继续当前授权的 Web 接入。未知状态不等于失败。若发现当前可复现的问题，说明具体结果后修复或调整范围。旧模型在浏览器不一定能打开，不能把 Blender 视图当 Web 验收。
- 不确定当前 three.js loader、压缩扩展或渲染 API 时，核对 three.js 官方文档及项目实际依赖版本；不要猜 API。

## 2. Web 副本与资源优化

- 原始 GLB/纹理保留不动；在明确的 Web 输出目录创建优化副本，记录输入与输出 hash、参数、运行时、日志和真实文件大小。按实际用户设备/交互和测量决定是否简化、裁剪或延迟加载；不套通用面数、单位或纹理尺寸上限。
- 用项目兼容的 `GLTFLoader` 加载 glTF/GLB。GLTFLoader 已处理 glTF 约定；坐标轴转换只能做一次。不要把 Blender Z-up 的相机位置/朝向数值原样搬到 three.js/Y-up，相机应按导入后场景包围范围和用户视角重新设定。
- 压缩选型分开衡量并记录：KTX2/Basis 用于纹理编码，需相应 loader/transcoder 并按当前 renderer 探测支持；Draco 压缩几何属性；Meshopt 作为其独立的网格压缩/解码路线。它们互不替代，也都不是必选项。按需启用，并在目标浏览器实测下载量、解码和显示效果。PNG/JPEG 传输字节数不等于纹理解码显存；分辨率、mipmap、格式/色彩空间、sampler 和多材质都会影响资源占用。
- 合批、纹理 atlas、实例化可能破坏对象拾取、分区或语义 ID。只有在可保持 `instance_id`/实例索引到场景对象的映射并验证射线拾取后才采用，不为减少 draw calls 强制合并整场景。

## 3. 材质、相机与交互

- 识别导出材质是否为 PBR 输入、烘焙纹理或照片重建表面。照片/扫描纹理可能已经包含阴影和环境光；不能仅按未烘焙 albedo 处理后再施加同强度灯光，否则会重复照明。将 Base Color、Metallic、Roughness、法线与颜色空间按实际纹理含义绑定；曝光和色调映射对比导出源及参考。
- 依据导入场景和目标设备配置相机、背景/环境、灯光、色彩管理与阴影。记录实际场景参数；不要假称与 Blender 同数值等效。
- 只实现用户要的交互。以 glTF node/用户映射保留对象选择；测试选中/取消选中、对象隐藏、切场景和资源释放。切换或卸载时对本场景不再使用的材质、贴图、几何、render target 和压缩解码器资源按所有权释放；共享资源仍被使用时不能提前 dispose。

## 4. 浏览器验证与交付

在实际浏览器运行本地页面并记录目标浏览器、设备/分辨率、测试场景和是否冷启动：

- 浏览器控制台/网络错误、模型请求与加载时间、解码/初始化等待；
- 首次真实渲染帧的观察方式和耗时；
- 稳态 FPS 的采样窗口/方法；
- `renderer.info` 等可读的纹理/几何对象计数，以及实际可测的进程/GPU 内存指标。若平台不公开显存就写“不可直接测量”，不得以估算值冒充实测显存。
- 对照已验收的参考角度检查裁切、尺寸观感、材质/色彩、透明度、阴影和交互语义；浏览器截图和性能记录留在任务输出目录。差异应定位到 loader、坐标、相机、材质/色管线或资产副本，并只重做受影响阶段。

交付可运行的本地项目入口、GLB/纹理来源与 hash、运行命令、实际浏览器结果、测量口径及未运行检查。只产出本地项目；外部部署、发布或上传必须有用户对该动作的明确授权。
